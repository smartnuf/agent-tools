# 0007: v0.2 product and distribution boundary

- Status: accepted
- Date: 2026-09-08
- Scope: ordinary-user command surface, release artifact boundary, and Agent Tools distribution channels
- Supersedes: the deferred WinGet/Homebrew discovery-channel direction in Decision 0001

## Decision

Make `agent-tools` the sole supported ordinary-user command-line interface.
Repository `scripts/` and clone launchers may remain as development, CI, release,
migration, or compatibility infrastructure, but released user workflows must not
require a repository checkout or a script path. Release artifacts should exclude
repository operational scripts unless a specific source-build or reproducibility
need justifies an explicitly documented exception.

Keep PyPI installed with `uv tool` as the one supported distribution channel for
Agent Tools itself for the foreseeable future. Retire the previously deferred
WinGet and Homebrew distribution-channel milestones and their implementation
queue as not planned. Do not replace them with MSI, cask/formula, deb/rpm,
standalone-binary, self-updater, or similar channel work merely for symmetry or
CI convenience.

A future alternative Agent Tools distribution channel requires a new decision
record backed by a concrete product requirement that PyPI/`uv tool` does not
satisfy, such as a material enterprise-policy requirement, a Python/uv bootstrap
barrier, required native OS lifecycle integration, or demonstrated user demand.
How Agent Tools provisions native capabilities through apt, WinGet, Homebrew,
dnf, pacman, Chocolatey, or another reviewed provider is independent of how
Agent Tools itself is distributed.

The minimally useful next release must expose native-capability installation
through the installed CLI. Its intended public shape includes:

```text
agent-tools install <capability> [<capability> ...]
```

That command must reuse the M3 capability catalogue, provider planning,
authorization, managed execution, provenance, rediscovery, verification, and
partial/uncertain recovery contracts. It must not introduce a second package
mapping or turn Agent Tools into an operating-system package manager.

## Reasons

- One install channel and one CLI reduce product, documentation, support, and
  compatibility surface while the core tool is still becoming minimally useful.
- M3 already contains the difficult provider-selection and safe-mutation
  machinery; hiding it behind clone bootstrap scripts prevents the packaged
  product from exposing its own principal capability.
- The existing WinGet/Homebrew distribution research adds maintenance and
  architectural work without solving a demonstrated near-term user problem.
- CI package-manager usage for Poppler, Ghostscript, or other native tools is
  evidence about native-provider integration, not evidence that Agent Tools
  needs another distribution channel.

## Consequences

- Installed-artifact tests must prove supported user workflows through
  `agent-tools`, not repository script paths.
- Clone scripts may delegate to the installed/public CLI or remain development
  helpers, but are not the product contract.
- The v0.2 planning slice includes a public `agent-tools install <list>` path and
  real-provider evidence where practical.
- M4a/M4b WinGet/Homebrew distribution tasks are retired as `not planned`; their
  historical research remains discoverable in GitHub history.
- Richer installation and discovery interfaces remain research topics until a
  later Intent/Characterise/Discover/Map cycle selects them.

## Reconsideration trigger

Reopen distribution-channel design only when new evidence identifies a user or
operational requirement that the PyPI/`uv tool` channel cannot reasonably meet.
Do not reopen it merely because another package manager exists or because a CI
fixture uses one.
